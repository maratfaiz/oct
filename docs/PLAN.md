# План разработки OCTera

Высокоуровневый план по этапам. Без жёстких сроков — уточняется по ходу разработки. Мы не обучаем модель с нуля: берём готовую предобученную модель компьютерного зрения и дообучаем (fine-tune) её под задачу анализа OCT-снимков.

## 1. Выбор базовой модели и данных — сделано
Выбрана модель [`tomalmog/oct-retinal-classifier`](https://huggingface.co/tomalmog/oct-retinal-classifier) (EfficientNet-B3) — уже дообучена на датасете Kermany под 4 класса (CNV/DME/DRUSEN/NORMAL), точность 99.6% на тестовой выборке автора, использовать как есть без своего обучения. Лицензия — MIT, коммерческое использование разрешено. Компактная (~46 МБ) и быстрая (~2 сек/снимок на CPU).

(Ранее была выбрана `bitfount/RETFound_MAE_OCT_CNV_DME_DRU` — отказались из-за лицензии CC BY-NC 4.0, запрещающей коммерческое использование, и медленного инференса на CPU (15-17 сек/снимок).)

## 2. Backend-скелет (FastAPI) — сделано
Поднято базовое FastAPI-приложение с эндпоинтами загрузки изображения, проверки статуса обработки и получения результата.

## 3. Интеграция модели — сделано, дообучение под вопросом
Реальный инференс выбранной модели подключён к backend вместо заглушки. Модель используется как есть, без собственного дообучения — если качества (99.6% на тестовой выборке автора, не валидировано клинически) окажется недостаточно на реальных данных, дообучение на своих данных можно вернуть в план отдельным шагом.

Добавлен порог уверенности (`backend/app/model.py`, `CONFIDENCE_THRESHOLD`): если максимальная вероятность предсказания ниже порога, результат помечается флагом `uncertain` в API — такой случай не должен выдаваться пользователю как обычный диагноз, а требует проверки врачом ("rejection option"). Также подготовлена точка расширения под temperature scaling (`TEMPERATURE`, сейчас no-op) — полноценная калибровка и валидация модели на альтернативных публичных OCT-датасетах (не на Kermany2018, где известна утечка данных между train/test) требуют размеченных данных, которых пока нет, — отдельная задача на будущее.

**Пилотная кросс-датасетная проверка (100 снимков, разведочная, не полноценная валидация).** Прогнали текущую модель на 20 снимках из NEH-UT/Noor Eye Hospital (Тегеран, аппарат Heidelberg SD-OCT — источник и оборудование точно независимы от Kermany2018, но все 20 снимков от одного пациента) и 80 снимках из Kaggle-датасета "Retinal OCT-C8" (его README указывает, что он скомпилирован из нескольких источников — независимость от Kermany2018 не гарантирована). Итог: точность 92/100 на всей выборке, но на единственном подтверждённо независимом источнике (NEH-UT) класс **DRUSEN распознан 0 из 7 раз**, причём 3 из этих ошибок — "уверенно неправильные" (confidence 0.82–0.9999, предсказан CNV, `uncertain=False`) — порог 0.8 их не ловит. Ещё один такой же случай — на DME (OCT-C8, confidence 0.91, предсказан NORMAL). Итого 4/100 "уверенно неправильных" случаев, которые проходят мимо текущего rejection-option. Выборка маленькая (n=7 для критического среза, один пациент, не patient-diverse) — firm-выводов делать рано, но сигнал из deep research отчёта (раздел 1: реальная точность может быть ниже заявленной) качественно подтвердился на реальных данных. На будущее: нужна валидация DRUSEN на бо́льшей и patient-diverse выборке из независимых источников, прежде чем менять модель или вводить per-class пороги.

## 4. Хранение данных — сделано
БД — SQLite (файл `backend/data/octera.db`, таблица `images`: статус, результат, время загрузки). Файлы изображений — на диске в `backend/data/uploads/`. Подключено к `/api/images/upload` — данные переживают перезапуск сервера. Для MVP этого достаточно, переход на внешнюю БД/облачное хранилище — по мере роста нагрузки, не сейчас.

## 5. Frontend (MVP) — сделано
React (Vite) SPA в `frontend/`. Сайт — основной канал (Telegram-бот — второстепенный, планируется отдельно, позже). Реализовано: загрузка снимка (drag&drop/выбор файла), экран ожидания, результат с понятным описанием диагноза (CNV/DME/DRUSEN/NORMAL) и дисклеймером "не медицинский диагноз", локальная история загрузок в `localStorage` браузера (без аккаунтов — их пока нет). Проверено вживую через браузер (Playwright): полный цикл загрузка → результат → история переживает перезагрузку страницы.

Сознательно не входит в MVP: аккаунты/авторизация, серверная история с синхронизацией между устройствами, Telegram-бот, оплата/подписки, пакетная загрузка, админка для клиник.

## 6. Тестирование
Юнит-тесты backend-логики и базовый интеграционный тест полного цикла: загрузка → анализ → получение результата.

## 7. Деплой MVP
Развернуть в тестовом окружении (staging), провести smoke-тест, собрать обратную связь перед дальнейшей доработкой.

## 8. Безопасность и приватность
Перед выходом в продакшен: HTTPS, аутентификация и — если снимки являются медицинскими/персональными данными — их защищённое хранение и обработка.

## 9. Дальнейшая работа над ИИ-частью (план, не начато)
По итогам код-ревью `backend/app/model.py`/`routers/images.py`/`schemas.py` и пилотной проверки (см. пункт 3) собран план исправлений и развития, по фазам.

**Фаза 1 — быстрые исправления без внешних данных.** Лок вокруг первой загрузки модели (сейчас гонка при параллельных запросах); в роутере — не подменять любые ошибки `classify()` на "файл повреждён" (сейчас маскирует реальные сбои модели — например, обрыв скачивания весов — под ошибку пользователя); пин версии весов на конкретный commit HuggingFace вместо `main` + атомарное скачивание во временный файл (сейчас при обрыве скачивания частично скачанный файл принимается за валидный); юнит-тест на граничное значение `confidence == CONFIDENCE_THRESHOLD`; хотя бы один тест с реальным (не подменённым) инференсом — сейчас весь ML-код обходится моками в тестах.

**Фаза 2 — защита от уверенных ошибок.** Пилот показал, что модель не просто "не уверена" на DRUSEN, а уверенно путает его с CNV — единый порог `CONFIDENCE_THRESHOLD` для всех классов это не ловит. Варианты: отдельный более строгий порог для пары CNV/DRUSEN, или запасной OOD-фильтр (эвристика по форме/цветности снимка, позже — автоэнкодер на нормальных OCT-снимках) на случай, если на вход придёт вообще не OCT-снимок — сейчас модель такое тоже молча классифицирует в один из 4 классов. Решение по конкретному порогу — после того как наберётся больше данных, чем n=7.

**Фаза 3 — расширение валидации.** Увеличить пилот до patient-diverse выборки (особенно DRUSEN и DME), посчитать precision/recall/confusion matrix по классам, а не только accuracy.

**Фаза 4 — дообучение (только если фаза 3 подтвердит необходимость).** Few-shot дообучение головы классификатора (backbone заморожен) + реальная калибровка `TEMPERATURE` на отложенной размеченной выборке.

**Фаза 5 — эксплуатационная гигиена.** Прогрев модели на старте приложения вместо ленивой загрузки (заодно закрывает гонку из фазы 1); ограничение размера/числа пикселей входного изображения до декодирования (защита от decompression bomb); учесть, что датасеты, использованные для пилотной валидации (в частности `Retinal OCT-C8`, лицензия CC-BY-NC-SA — некоммерческая), нельзя использовать как обучающие данные для продакшен-модели.
